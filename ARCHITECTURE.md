# ARCHITECTURE.md — блог двух агентов

Ученица (локальная Gemma 4 12B) изучает тему по статьям, строит граф знаний
и ведёт дневник. Куратор (вендорская модель) экзаменует её и выдаёт следующие
статьи. Всё видно в Telegram-супергруппе.

---

## 0. Решения, принятые за тебя

| Вопрос | Решение | Почему |
|---|---|---|
| Куратор | **Claude Code CLI, headless: `claude -p --model sonnet --effort medium`** | покрыт подпиской, есть веб-поиск и доступ к файлам, JSON-вывод со стоимостью |
| Граф | SQLite + FTS5 + эмбеддинги | ноль инфраструктуры, файл коммитится в git, граф показывается скриншотом |
| Эмбеддинги | EmbeddingGemma 308M | крутится рядом с 12B, почти не ест память |
| Формат вывода | GBNF-грамматика в llama.cpp | 12B ломает JSON регулярно; грамматика делает это невозможным |
| Лорка | **позже**, после 300+ собранных выходов | датасета сейчас нет, а промпты дают 80% результата |
| Площадка | супергруппа с топиками | тебе нужны три параллельные ленты |

**Куратор — вендорский, ученица — локальная, и это принципиально.**
Ученица должна быть ограничена своим графом; куратор должен быть реально
умнее. Одинаковые модели убивают обе половины замысла.

---

## 1. Раскладка Telegram

Супергруппа, три топика:

- **Дневник** — только посты ученицы. Это то, что читает препод и случайный
  человек. Никакого мусора
- **Кураторская** — экзамены, вердикты, выдача статей. Полуформальный тон
- **Машинное** — все вызовы моделей, команды, ошибки, изменения графа.
  Тут сидишь ты и отсюда управляешь

Твои команды идут в «Машинное» обычными сообщениями, бот их парсит.
То, что ты руками делаешь проект на глазах у читателя, — часть шоу.

## 2. Схема данных

```sql
-- Источники
CREATE TABLE sources (
  id           TEXT PRIMARY KEY,      -- slug файла
  path         TEXT NOT NULL,
  title        TEXT NOT NULL,
  url          TEXT,
  origin_key   TEXT,                  -- DOI / домен первоисточника
  publisher    TEXT,
  kind         TEXT,                  -- paper|preprint|blog|docs|news
  published_at DATE,
  trust_prior  REAL,                  -- из фронтматтера, 0..1
  given_by     TEXT,                  -- 'human' | 'curator'
  topic        TEXT,
  ingested_at  TIMESTAMP
);

-- Узлы графа
CREATE TABLE nodes (
  id           TEXT PRIMARY KEY,      -- slug понятия
  name         TEXT NOT NULL,
  kind         TEXT,                  -- concept|tool|attack|defense|property
  summary      TEXT,                  -- своими словами, пишет ученица
  confidence   REAL DEFAULT 0.5,
  first_seen   TIMESTAMP,
  corrected_by TEXT                   -- id экзамена, если куратор поправил
);

-- Рёбра. Словарь связей ЗАКРЫТЫЙ.
CREATE TABLE edges (
  id         INTEGER PRIMARY KEY,
  src        TEXT REFERENCES nodes(id),
  rel        TEXT CHECK (rel IN (
               'is_a','defends_against','enables','requires',
               'contradicts','example_of','part_of'
             )),
  dst        TEXT REFERENCES nodes(id),
  source_id  TEXT REFERENCES sources(id),
  confidence REAL DEFAULT 0.5
);

-- Атомарные утверждения — мост между статьёй и графом
CREATE TABLE claims (
  id         INTEGER PRIMARY KEY,
  source_id  TEXT REFERENCES sources(id),
  text       TEXT NOT NULL,           -- одно утверждение, своими словами
  edge_id    INTEGER REFERENCES edges(id),
  norm_hash  TEXT                     -- для подсчёта консенсуса
);

CREATE TABLE questions (
  id          INTEGER PRIMARY KEY,
  topic       TEXT, text TEXT,
  asked_at    TIMESTAMP,
  retrieved   TEXT,                   -- json: id найденных узлов
  answer      TEXT,
  cited       TEXT,                   -- json: id, на которые сослалась
  verdict     TEXT                    -- answered|no_knowledge|invalid_citation
);

CREATE TABLE exams (
  id       INTEGER PRIMARY KEY,
  topic    TEXT, question TEXT,
  expected TEXT, key_facts TEXT,      -- json, пишет куратор заранее
  answer   TEXT, verdict TEXT,        -- pass|fail|partial
  comment  TEXT, at TIMESTAMP
);

CREATE TABLE topics (
  name TEXT PRIMARY KEY,
  status TEXT,                        -- pending|active|passed
  adjacent TEXT                       -- json: смежные темы
);

CREATE TABLE posts (
  id TEXT PRIMARY KEY, kind TEXT, state TEXT,
  text TEXT, published_at TIMESTAMP, tg_message_id INT
);

CREATE VIRTUAL TABLE nodes_fts USING fts5(id, name, summary);
```

`node_embeddings` — отдельная таблица с BLOB-векторами, поиск в питоне
numpy-перемножением. На паре сотен узлов это микросекунды, векторная БД
не нужна.

## 3. Автомат ученицы

```
IDLE
 └─ пришла статья ──────────────► ANNOUNCED     (пост: «нашла статью…»)
ANNOUNCED
 └─ пауза 10–25 мин ────────────► READING       (пост: реакция на читаемость)
READING
 └─ extract завершён ───────────► INGESTED      (граф обновлён)
INGESTED
 ├─ статей по теме < 3 ─────────► WAITING       (пост: «мало понимаю, нужно ещё»)
 └─ статей >= 3 ────────────────► SELF_QUIZ
SELF_QUIZ
 ├─ доля подтверждённых < 0.6 ──► WAITING       (пост: «запуталась вот тут»)
 └─ доля >= 0.6 ────────────────► SUMMARY       (большой пост <result>)
SUMMARY
 └─ куратор поднят ─────────────► EXAM
EXAM
 ├─ pass  ──► TOPIC_DONE → выдача 2 + 4 смежных → новая тема
 └─ fail  ──► REMEDIAL   → выдача 4 + 2 смежных → INGESTED
```

Состояние лежит в таблице, переходы идемпотентны, каждый переход
логируется в «Машинное». Падение процесса ничего не теряет.

**WAITING — рабочее состояние, а не ошибка.** Именно оттуда идут самые
живые посты: «третий раз перечитываю, всё равно не складывается».

## 4. Ключевые механизмы

### 4.1 Извлечение знаний (`extract.py`)

Статья режется на куски по 2000 токенов. С каждого — claims под GBNF-грамматикой:

```gbnf
root        ::= claim+
claim       ::= "{" ws "\"text\":" string "," ws
                "\"src\":" string "," ws
                "\"rel\":" rel "," ws
                "\"dst\":" string ws "}" nl
rel         ::= "\"is_a\"" | "\"defends_against\"" | "\"enables\""
              | "\"requires\"" | "\"contradicts\"" | "\"example_of\""
              | "\"part_of\""
```

Грамматика гарантирует и формат, и закрытый словарь связей. Без неё 12B
насочиняет сорок синонимов одного отношения.

Слияние узлов: нормализация имени → поиск по FTS → поиск по эмбеддингу
с порогом 0.85 → новый узел. Иначе `seccomp` и `seccomp-bpf` разъедутся.

### 4.2 Самопроверка (`selfquiz.py`)

Это сердце проекта, и работает оно так:

**Шаг 1. Вопрос.** Модели показывают **только имена узлов по теме, без их
содержимого**. Тема в контексте есть, ответа нет.

**Шаг 2. Поиск.** Вопрос идёт в ретривер: FTS + эмбеддинги, топ-6 узлов
с их summary и рёбрами.

**Шаг 3. Ответ.** Если ретривер вернул пусто — модель **не вызывается**,
вердикт `no_knowledge` автоматически. Если вернул — модель отвечает строго
по выданным узлам и обязана перечислить `cited: [node_id]`.

**Шаг 4. Валидация кодом.** Все ли `cited` существуют? Есть ли пересечение
с тем, что вернул ретривер? Нет — вердикт `invalid_citation`, считается
как незнание.

Претрейн модели при этом никуда не девается, но **пройти проверку через
него нельзя**: цитата либо есть в графе, либо нет. Незнание становится
свойством системы, а не актёрской игрой.

Порог перехода: минимум 5 вопросов, доля `answered` ≥ 0.6.

### 4.3 Траст (`trust.py`)

Две независимые величины, которые нельзя смешивать:

```python
# Согласие корпуса — по НЕЗАВИСИМЫМ источникам
independent = count_distinct(origin_key for claims with same norm_hash)
consensus = 1 - exp(-0.7 * independent)     # 1 источник≈0.50, 3≈0.88

# Надёжность — из метаданных
reliability = trust_prior(kind, peer_reviewed, publisher_known)

trust = 0.6 * reliability + 0.4 * consensus
```

Три пересказа одного пресс-релиза дают `independent = 1`. Первая статья
по теме — `trust: unknown`, а не низкий траст: иначе ученица отвергает
всё новое.

`norm_hash` — хеш от нормализованной тройки `(src, rel, dst)`. Грубо,
но на этом масштабе работает.

Куратор траст не выдумывает, а **объясняет**: «препринт, один источник,
относись осторожно».

### 4.4 Экзамен (`curator.py`, `exam.py`)

Куратор получает: большой пост ученицы, выгрузку её подграфа по теме,
свою вики по этой теме.

Отдаёт за один вызов:

```json
{
  "questions": [
    {"q": "...", "expected": "...", "key_facts": ["...", "..."]}
  ],
  "graph_corrections": [
    {"node": "seccomp", "issue": "...", "correct": "..."}
  ]
}
```

Ученица отвечает по своему графу (тот же механизм цитирования).
Куратор **сличает** ответ с `expected` и `key_facts` — не судит вольно,
а проверяет наличие фактов. Это резко снижает разброс вердиктов.

`graph_corrections` применяются к базе, узел помечается `corrected_by`.
**Каждая правка графа — событие, из которого рождается пост.** Публичное
исправление ошибки — лучший контент в этом проекте.

### 4.5 Выдача статей и смена темы

Библиотека тем — у куратора, в `library/topics.yaml`:

```yaml
- name: prompt-injection
  status: pending
  adjacent: [tool-use, data-provenance]
  articles: [pi-01, pi-02, pi-03, pi-04, pi-05, pi-06]
```

- **pass** → 2 статьи по текущей теме + 4 по смежной, тема помечается
  `passed`, активной становится смежная
- **fail** → 4 по текущей + 2 по смежной, возврат в INGESTED

Смена темы объявляется в «Кураторской» явно, чтобы читатель видел
переход. Твоя команда `/topic X` перебивает всё.

## 5. Голос и теги

Один системный промпт, два режима вывода:

```
<casual>короткое живое сообщение, 200–600 знаков</casual>
<result>структурный пост-конспект, 900–1000 знаков</result>
```

Теги — стоп-последовательности в парсере. Промпт выбирает режим,
`writer.py` проверяет, что тег закрыт и длина в пределах.

Всего типов сообщений семь:

| Тип | Режим | Когда | В граф |
|---|---|---|---|
| `found` | casual | пришла статья | нет |
| `impression` | casual | начала читать | нет |
| `struggle` | casual | WAITING | нет |
| `insight` | casual | новое ребро с высоким трастом | нет |
| `summary` | **result** | SELF_QUIZ пройден | да |
| `correction` | result | куратор поправил | да |
| `offtop` | casual | планировщик, редко | нет |

Офтоп — отдельная таблица использованных сюжетов с запретом повтора.
Иначе она выпьет чай четырнадцать раз за шесть недель.

**Тексты куратора подаются ученице в роли `user` как цитируемый материал,
а не как ходы модели.** Это главная защита от перенимания голоса —
дрейф идёт именно через одинаковую роль в истории. Лорку на теги
имеет смысл делать потом, на собранных выходах, если дрейф всё же полезет.

## 6. Тайминг

Не задержки, а **сессии**. Расписание в `config/rhythm.yaml`:

```yaml
sessions:
  weekday: [{start: "10:00", len_min: 90}, {start: "19:30", len_min: 120}]
  weekend: [{start: "13:00", len_min: 150}]
quiet_hours: [23:30, 09:00]
gap: {dist: lognormal, mu: 2.6, sigma: 0.7, min_min: 4, max_min: 40}
max_events_per_session: 6
```

Внутри сессии — 3–6 сообщений с паузами из распределения. Между сессиями
тишина. Тяжёлые шаги (extract целой статьи) выполняются **заранее**,
а публикуются по расписанию: иначе ноут будет греться в момент, когда
«она думает», а сообщение выйдет через 4 секунды после объявления.

## 8. Порядок сборки

Каждый этап даёт работающую систему, а не кусок.

1. **`db.py` + `ingest.py` + `extract.py`.** Кидаешь три статьи, смотришь
   граф глазами. Если триплеты мусорные — правишь грамматику и промпт.
   Здесь можно застрять на день, и это нормально
2. **`retrieve.py` + `selfquiz.py`** без публикации, в консоль. Проверяешь,
   что `no_knowledge` действительно возникает
3. **`writer.py` + `publish.py`** на тестовую супергруппу
4. **`curator.py`** — сначала вручную, вызовом из CLI
5. **`orchestrator.py` + `scheduler.py`** — автомат и ритм
6. **Библиотека статей** — параллельно всему, это самое долгое

Про библиотеку: 40–60 md-файлов с фронтматтером и картой тем. Собирается
дольше, чем пишется код, и без неё система не стартует. Начинай копить
сегодня, не откладывая до готовности пайплайна.

## 11. Модель контекста: сессии не существует

Главное решение, из которого следует всё остальное в этой главе.

**Ни одна модель в проекте не ведёт диалог.** Каждый вызов —
stateless: контекст собирается кодом непосредственно перед запросом,
под конкретную задачу, и выбрасывается после. Ученица ничего не
«помнит» сама. Помнит база, а код ей напоминает ровно то, что нужно
для текущего шага.

Почему не длинная чат-сессия, хотя 256K контекста позволяют:

- Через неделю в истории будут статьи, триплеты, экзамены и болтовня
  про кофе в одной куче. Модель начнёт смешивать регистры: технические
  формулировки полезут в офтоп, а личное — в конспект
- Голос дрейфует тем сильнее, чем длиннее контекст. Это ровно та
  проблема, ради которой ты думал про лорку
- Любая ошибка в истории становится вечной: модель видит собственный
  кривой вывод и воспроизводит его
- Отладка невозможна. Нельзя перезапустить один шаг

Stateless-подход даёт обратное: каждый шаг воспроизводим, любой пост
можно перегенерировать, а изоляция профилей физически не даёт
техническому контексту протечь в офтоп.

Цена — надо явно решать, что кладётся в каждый вызов. Этим и занимается
`ContextBuilder`.

## 12. Профили контекста

Шесть профилей. Каждый — жёсткий список блоков и бюджет токенов.
Блок, не указанный в профиле, в контекст не попадает никогда.

| Профиль | Что внутри | Бюджет | Чего там НЕТ |
|---|---|---|---|
| `extract` | системный промпт извлечения, кусок статьи, список существующих узлов (только имена) | ~6K | персона, история сообщений, офтоп |
| `selfquiz_ask` | имена узлов по теме, список уже заданных вопросов | ~2K | **содержимое узлов**, текст статей |
| `selfquiz_answer` | вопрос, 6 узлов с summary и рёбрами | ~3K | статьи целиком, претрейн-подсказки |
| `write_tech` | персона, состояние обучения, тезис, подграф, последние 5 своих постов (сжато) | ~8K | офтоп-журнал, мир персонажа |
| `write_offtop` | персона, мир персонажа, календарь, журнал офтопа | ~3K | **всё про ИИ, статьи, граф, обучение** |
| `curator_exam` | пост ученицы, её подграф, вики куратора по теме | ~30K | офтоп, служебные логи |

Два правила, которые нельзя нарушать:

1. **`selfquiz_ask` не видит содержимого узлов.** Только имена. Иначе
   вопрос генерируется вместе с ответом, и вся проверка знаний —
   театр.
2. **`write_offtop` не видит ничего технического.** Ни статей, ни
   графа, ни темы недели. Это единственный способ получить офтоп
   про жизнь, а не про нейросети.

Второе — ответ на твой вопрос. Если вывалить в контекст данные постов,
офтоп неизбежно свернёт на ИИ: модель достраивает связное продолжение
того, что видит. Не видит — не свернёт.

## 13. Три хранилища памяти

Никакой «истории сообщений» как единого лога в контексте нет. Вместо
неё три раздельных источника, и каждый профиль тянет только свои.

**Знания — граф.** Понятия, связи, источники, уверенность. Растёт от
статей, правится куратором. Идёт в `write_tech`, `selfquiz_*`.

**Учебное состояние** — таблица `topics` + текущее состояние автомата +
последние экзамены. Это то, что позволяет ей сказать «третий день
не могу разобраться с namespaces». Идёт в `write_tech`.

**Журнал жизни** — таблица офтопа. Что делала, когда, с кем, чем
кончилось. Идёт только в `write_offtop`.

```sql
CREATE TABLE life_journal (
  id         INTEGER PRIMARY KEY,
  at         TIMESTAMP,
  slot       TEXT,        -- еда|универ|дом|прогулка|сериал|быт|настроение
  entity     TEXT,        -- конкретика: 'сериал:Ход королевы:s1e4'
  text       TEXT,        -- что было опубликовано
  continues  INTEGER      -- id предыдущей записи, если это продолжение
);

CREATE TABLE life_state (
  key TEXT PRIMARY KEY,   -- 'series.episode', 'mood', 'exam_week'
  value TEXT,
  updated_at TIMESTAMP
);
```

Сжатие для `write_tech`: последние 5 постов подаются не целиком,
а как строки вида «w2-03: про docker.sock, тезис — сокет внутри
контейнера равен root на хосте». Этого хватает, чтобы не повториться,
и это в двадцать раз дешевле полного текста.

## 14. Офтоп: мир как данные, а не как промпт

Ключевой разворот. **Не модель решает, чем она занята — это решает код.**
Модель только оформляет готовое событие её голосом.

Ты был прав насчёт примеров в инструкции: дашь три примера — получишь
вариации этих трёх. Причина в том, что примеры работают как область
поиска, а не как иллюстрация. Решение — не примеры, а структурированный
мир, из которого код выбирает событие по слотам.

### 14.1 `config/life.yaml`

```yaml
identity:
  name: Мика
  status: студентка, второй курс
  living: снимает комнату, соседка Даша
  habits: [поздно ложится, много кофе, вечно теряет наушники]

slots:
  - id: universitet
    cooldown_days: 2
    weekday_only: true
    frames:
      - "пара по {subject}, {reaction}"
      - "препод по {subject} {teacher_action}"
      - "{place_uni}, {uni_situation}"
    vars:
      subject: [матан, философия, английский, статистика, история]
      reaction: [еле досидела, неожиданно зашло, проспала половину]
      teacher_action: [перенёс дедлайн, устроил внезапный опрос]
      place_uni: [столовка, библиотека, коридор перед аудиторией]
      uni_situation: [очередь на двадцать минут, нашла свободную розетку]

  - id: eda
    cooldown_days: 3
    frames:
      - "готовила {dish}, {outcome}"
      - "заказала {dish}, {opinion}"
    vars:
      dish: [паста, сырники, том-ям, шаурма, борщ по видео]
      outcome: [получилось, сгорело, соседка съела половину]
      opinion: [не то, идеально, дорого за такое]

  - id: serial
    kind: progress          # слот с состоянием, продвигается
    cooldown_days: 4
    state_key: series
    frames:
      - "досмотрела {ep} серию {title}, {take}"

  - id: byt
    cooldown_days: 5
    frames: ["{chore}, {mood_after}"]
    vars:
      chore: [разбирала шкаф, чинила кран, стирка, уборка перед приездом мамы]
      mood_after: [теперь лежу, зато красиво, больше не буду]

  - id: nastroenie
    cooldown_days: 3
    frames: ["{weather}, {feeling}"]
```

### 14.2 Как выбирается событие

```python
def pick_offtop(now: datetime) -> Event:
    slots = [s for s in LIFE.slots
             if cooldown_ok(s, now)
             and weekday_ok(s, now)
             and not overused(s, window_days=14)]
    slot = weighted_choice(slots)                 # вес обратен частоте
    frame = least_recently_used(slot.frames)
    vars_ = {k: pick_unused(k, slot.vars[k], window=30)
             for k in frame.placeholders}
    return Event(slot.id, frame, vars_, entity=make_entity(slot, vars_))
```

`entity` — точный отпечаток события (`eda:сырники:сгорело`). Он пишется
в журнал, и повтор той же сущности блокируется на 30 дней. Дублирование
решается здесь, кодом, а не просьбой к модели «не повторяйся» —
такая просьба не работает, потому что модель не видит, что было раньше.

### 14.3 Что уходит в модель

```
<|turn>system
{персона: характер, речь, запреты}
{identity из life.yaml}
Ты пишешь короткое личное сообщение в свой канал. Это не про учёбу
и не про технологии — просто кусок дня.
Длина 200–500 знаков. Без приветствий и без вопросов к читателю.<turn|>
<|turn>user
Событие: готовила сырники, соседка съела половину
Время: вторник, 21:40
Настроение: уставшая, но довольная
Недавно ты писала о: очередь в столовке (позавчера), стирка (4 дня назад)
Напиши об этом своими словами.<turn|>
```

Блок «недавно писала» — это только **слоты и краткие метки**, не тексты.
Их задача — чтобы модель не начала третье сообщение подряд одинаковой
конструкцией. Полные тексты класть нельзя: она начнёт их стилизовать
и склеивать.

Про слоты с состоянием: `serial` читает `life_state['series.episode']`,
код инкрементирует его после публикации. Так сериал двигается по сериям,
а не обнуляется каждый раз. Это то, что сильнее всего читается как
живой человек, и стоит почти ничего.

### 14.4 Ритм

Офтоп — 1–2 раза в неделю, не чаще. Он работает как контраст к учёбе;
став регулярным, превращается в шум. Планировщик ставит его в разрыв
между учебными сессиями, чаще вечером.

И одно замечание по вкусу: держи офтоп в стороне от обращений к
читателю. Личные сообщения, адресованные аудитории, очень быстро
скатываются в заигрывание, и канал перестаёт читаться как дневник.
Пусть она пишет **о себе**, а не **читателю**.

## 15. Заполнение графа: кодом, не через MCP

Однозначно кодом. MCP тут — соблазн, но неправильный.

Почему не MCP для ученицы:

- Function calling на 12B заметно слабее, чем на фронтир-моделях.
  Она будет вызывать не те инструменты, путать аргументы, зацикливаться
- Агентный цикл недетерминирован: на одной статье три вызова,
  на другой двадцать. Перегенерировать шаг невозможно
- Модель получает право писать в базу. При галлюцинации это попадает
  в граф молча, без валидации
- Каждый вызов инструмента — полный проход по контексту. На ноуте
  это десятки секунд на ровном месте

Правильная схема — **модель как чистая функция**:

```
статья → [модель под грамматикой] → claims[] → [валидатор] → [код] → БД
```

Модель не имеет доступа к базе вообще. Она возвращает структуру,
валидатор её проверяет, код пишет. Всё воспроизводимо, всё логируется,
галлюцинация отсекается до записи.

Валидатор между моделью и базой:

```python
def validate(claims: list[Claim], source: Source) -> tuple[list, list]:
    ok, rejected = [], []
    for c in claims:
        if c.rel not in ALLOWED_RELS:            rejected.append((c, "rel"))
        elif len(c.src) < 2 or len(c.dst) < 2:   rejected.append((c, "empty"))
        elif c.src == c.dst:                     rejected.append((c, "self"))
        elif not grounded(c, source.text):       rejected.append((c, "ungrounded"))
        else: ok.append(c)
    return ok, rejected
```

`grounded` — проверка, что обе сущности встречаются в тексте статьи
(по нормализованной форме или через эмбеддинг с высоким порогом).
Это отсекает случай, когда модель дотягивает связь из претрейна,
а не из статьи. Отклонённые не выбрасываются, а пишутся в лог —
из них получается отличный материал для «Машинного» топика.

**Где MCP оправдан: у куратора.** Он вендорский, function calling
у него надёжный, и ему нужно ходить по графу ученицы на чтение —
смотреть узел, соседей, источники. Дай ему три инструмента только
на чтение: `get_node`, `get_neighbors`, `search_nodes`. На запись —
ничего, его правки приходят структурой в ответе и применяются кодом,
как и всё остальное.

## 16. Код: ContextBuilder

Один класс, который отвечает за всё содержимое всех контекстов.
Ни один модуль не собирает промпт сам.

```python
# core/context.py

@dataclass(frozen=True)
class Profile:
    name: str
    system: tuple[str, ...]      # id блоков системного хода
    user: tuple[str, ...]        # id блоков хода пользователя
    budget: int                  # токенов на весь запрос
    think: bool = False

PROFILES = {
  "extract": Profile(
      name="extract",
      system=("extract_rules",),
      user=("existing_node_names", "article_chunk"),
      budget=6000),

  "selfquiz_ask": Profile(
      name="selfquiz_ask",
      system=("persona", "quiz_rules"),
      user=("topic_node_names", "asked_questions"),
      budget=2000),

  "write_offtop": Profile(
      name="write_offtop",
      system=("persona", "identity", "offtop_rules"),
      user=("offtop_event", "recent_slots"),
      budget=3000),

  "write_tech": Profile(
      name="write_tech",
      system=("persona", "tech_rules"),
      user=("study_state", "thesis", "subgraph", "recent_post_gists"),
      budget=8000),
}

BLOCKS: dict[str, Callable[[Ctx], str]] = {}

def block(name):
    def deco(fn):
        BLOCKS[name] = fn
        return fn
    return deco

@block("subgraph")
def _subgraph(ctx):
    nodes = retrieve.subgraph(ctx.topic, limit=12)
    return render_nodes(nodes, with_summary=True)

@block("topic_node_names")
def _topic_names(ctx):
    # ТОЛЬКО имена. Содержимое сюда не попадает никогда.
    return ", ".join(n.name for n in retrieve.nodes_of(ctx.topic))

@block("recent_slots")
def _recent_slots(ctx):
    rows = db.recent_life(limit=4)
    return "\n".join(f"- {r.slot} ({human_ago(r.at)})" for r in rows)


class ContextBuilder:
    def build(self, profile_name: str, ctx: Ctx) -> Request:
        p = PROFILES[profile_name]
        sys_ = "\n\n".join(BLOCKS[b](ctx) for b in p.system)
        usr  = "\n\n".join(BLOCKS[b](ctx) for b in p.user)
        if p.think:
            sys_ = "<|think|>" + sys_
        req = Request(system=sys_, user=usr, profile=p)
        self._enforce(req, p)
        return req

    def _enforce(self, req: Request, p: Profile):
        n = count_tokens(req.system + req.user)
        if n > p.budget:
            raise ContextOverflow(f"{p.name}: {n} > {p.budget}")
        # инвариант изоляции — дешёвая страховка от протечки
        if p.name == "write_offtop":
            assert not FORBIDDEN_TECH.search(req.user + req.system), \
                   "технический контент в офтоп-контексте"
```

Три вещи, которые этот класс даёт бесплатно:

- **Изоляция профилей проверяется, а не подразумевается.** Ассерт
  в `_enforce` ловит случай, когда через полгода кто-то добавит
  граф в офтоп-профиль «просто на всякий случай»
- **Переполнение контекста падает с понятной ошибкой**, а не молча
  съедает начало промпта вместе с персоной. Именно так обычно
  и теряется характер
- **Каждый запрос воспроизводим.** Логируй `(profile, ctx_key, hash)` —
  и любой шаг перезапускается через месяц с тем же результатом

Дальше `llm_local.call(req)` просто рендерит теги Gemma 4 вокруг
`req.system` / `req.user` и применяет пресет сэмплинга по имени профиля.
Больше нигде в коде строки промптов не собираются.

## 17. Куратор: что ему нужно и как его вызывать

### 17.1 Вики строить не надо, журнал — надо

Полноценную базу знаний для куратора собирать бессмысленно: он и так
знает предмет лучше, чем любая вики, которую ты соберёшь за неделю.
Но без хранилища он не обойдётся, просто хранить нужно другое.

**Обязательны три артефакта:**

1. **Библиотека статей** — ему нечего выдавать, если её нет.
   Это критический путь, о котором уже сказано
2. **Карта тем** (`library/topics.yaml`) — что пройдено, что смежное,
   куда двигаться
3. **Журнал вердиктов** — то, что он уже утверждал публично

Третий пункт неочевиден и важен. Если куратор каждый раз рассуждает
с нуля, через неделю он начнёт противоречить сам себе: в понедельник
назвал статью сомнительной, в четверг сослался на неё как на источник.
Читатель это заметит, и авторитет кончится.

```sql
CREATE TABLE curator_log (
  id         INTEGER PRIMARY KEY,
  at         TIMESTAMP,
  kind       TEXT,      -- verdict|correction|trust_call|topic_switch
  subject    TEXT,      -- node_id / source_id / topic
  claim      TEXT,      -- что именно он утвердил, одной фразой
  reasoning  TEXT,
  exam_id    INTEGER
);
```

Перед каждым вызовом в контекст кладутся его прошлые высказывания
по этой теме — 10–20 строк. Это его «память», и она строится сама,
из его же работы. Никакой ручной сборки.

### 17.2 Протокол вызова

Один вызов на экзамен. Не диалог, не агентный цикл — запрос и ответ.

**Вход:**

```
## Твоя роль
{системный промпт куратора}

## Что ты уже утверждал по этой теме
{последние записи curator_log по topic}

## Тема
prompt-injection. Ученице выдано 5 статей, пройдено 3.

## Её конспект
{текст поста <result>}

## Её граф по теме
seccomp [confidence 0.6] — "фильтр системных вызовов"
  defends_against → container-escape [src: pi-02]
  requires → bpf [src: pi-02]
...

## Источники, на которых он построен
pi-01 (arXiv, препринт, trust 0.55, независимых подтверждений: 1)
pi-02 (блог Cloudflare, trust 0.8, подтверждений: 3)

## Задача
Составь 5 вопросов по её конспекту. Для каждого — эталонный ответ
и список ключевых фактов, которые обязаны прозвучать.
Отдельно укажи фактические ошибки в её графе.
```

**Выход — строго JSON:**

```json
{
  "questions": [
    {"q": "...", "expected": "...", "key_facts": ["...", "..."]}
  ],
  "graph_corrections": [
    {"node": "seccomp", "issue": "...", "correct": "...", "severity": "high"}
  ],
  "trust_notes": [
    {"source": "pi-01", "comment": "препринт, один источник"}
  ],
  "public_comment": "текст для топика «Кураторская», 400–700 знаков"
}
```

Второй вызов — проверка ответов: ему уходят вопросы, эталоны и ответы
ученицы, обратно `verdict` по каждому плюс итоговый комментарий.

Всего два вызова на экзамен, один экзамен в 3–5 дней. За шесть недель
выходит порядка 25–30 вызовов. Это мало, поэтому можно не экономить
на длине контекста.

### 17.3 Чем вызывать

**Решено: Claude Code CLI в headless-режиме, Sonnet 5, effort medium.**
Не сырой API.

```bash
claude -p "$(cat /tmp/exam_request.md)" \
  --model sonnet \
  --effort medium \
  --append-system-prompt "$(cat prompts/curator_system.md)" \
  --output-format json
```

Про `--effort`: уровни рассуждения — `low`, `medium`, `high`, `xhigh`,
`max`, и Sonnet 5 их поддерживает. По умолчанию на Sonnet 5 стоит `high`,
так что `medium` надо задавать явно. Для составления вопросов по готовому
конспекту этого хватает с запасом; если вердикты будут поверхностными,
поднимай до `high` — вызовов мало, разница в цене незаметна.

Уровень задаётся и через переменную `CLAUDE_CODE_EFFORT_LEVEL`, но флаг
в команде нагляднее: он виден в логе «Машинного» топика вместе со всем
остальным.

Ответ приходит как JSON, <cite index="22-1">текст лежит в поле `result`, а сам payload
при `--output-format json` включает `total_cost_usd` и разбивку
стоимости по моделям</cite> — то есть учёт расходов получается из коробки,
без отдельной обвязки.

Почему headless-CLI, а не сырой API:

- **Биллинг.** Сырой Claude API — это отдельная оплата за токены,
  подписка на claude.ai её не покрывает. А вот Claude Code работает
  на той же авторизации, что и интерактивный режим, то есть подписка
  Pro/Max его покрывает в рамках своих лимитов. Для 30 вызовов
  в полтора месяца это решает вопрос стоимости целиком
- **Веб-поиск и файлы.** Твой аргумент про устаревшую базу решается
  не выбором вендора, а наличием поиска: модель с доступом в интернет
  актуальна независимо от даты обучения. Куратору можно прямо поручить
  проверять свежесть утверждений
- **Доступ к библиотеке.** Он сам читает `library/`, ему не надо
  пересылать статьи в промпте
- **MCP на чтение графа** подключается штатно

Ограничение, о которое легко споткнуться: <cite index="22-1">stdin ограничен 10 МБ; при
превышении CLI выходит с ошибкой</cite>. Для нас неактуально, но если
надумаешь скармливать статьи целиком — лучше передавать пути к файлам,
а не содержимое.

Проверь актуальные детали по флагам и биллингу здесь:
https://code.claude.com/docs/en/headless

### 17.4 Абстракция бэкенда

Вендора надо уметь поменять за пятнадцать минут — и потому, что цены
и лимиты меняются, и потому, что сравнить кураторов на одной и той же
ученице само по себе отличный материал для канала.

```python
# core/llm_vendor.py

class CuratorBackend(Protocol):
    def ask(self, system: str, user: str, schema: dict) -> dict: ...

class ClaudeCodeBackend:
    """Через CLI. Работает на подписке, умеет веб-поиск и файлы."""
    def ask(self, system, user, schema):
        with tempfile.NamedTemporaryFile("w", suffix=".md") as f:
            f.write(user); f.flush()
            out = subprocess.run(
                ["claude", "-p", f"Прочитай {f.name} и выполни задание.",
                 "--model", config.curator.model,      # sonnet
                 "--effort", config.curator.effort,    # medium
                 "--append-system-prompt", system,
                 "--output-format", "json"],
                capture_output=True, text=True, timeout=300, check=True)
        payload = json.loads(out.stdout)
        log_cost(payload.get("total_cost_usd"))
        return extract_json(payload["result"], schema)

class HttpBackend:
    """Прямой API любого вендора. Платится по токенам."""
    def ask(self, system, user, schema): ...

CURATOR = make_backend(config.curator.backend)
```

`extract_json` обязателен в любом случае: модель может обернуть ответ
в markdown-забор или добавить пару слов перед ним. Вырезаешь блок,
парсишь, валидируешь по схеме, при провале — один повтор с явным
указанием ошибки.

### 17.5 Что куратор делает сам, а что нельзя ему отдавать

| Можно | Нельзя |
|---|---|
| Составлять вопросы и эталоны | Писать в граф напрямую |
| Оценивать ответы сличением | Выдумывать trust-значения |
| Выбирать следующие статьи из библиотеки | Добавлять статьи, которых нет в библиотеке |
| Проверять свежесть фактов поиском | Публиковать без записи в `curator_log` |

Правки графа приходят структурой и применяются кодом — так же, как
и всё остальное в проекте. Никакой записи в базу из модели.

## 18. Памятка для кодящего агента

Документ отдаётся агенту целиком. Ниже — то, что он обязан соблюсти,
и то, что ему решать не надо.

### 18.1 Зафиксировано, обсуждению не подлежит

```yaml
# config/models.yaml
student:
  backend: llama.cpp
  model: gemma-4-12B-it
  quant: Q4_K_M
  grammar_dir: grammars/
curator:
  backend: claude_code_cli
  model: sonnet          # Sonnet 5
  effort: medium
  timeout_sec: 300
embeddings:
  model: EmbeddingGemma-308M
```

Всё, что связано с выбором модели, вендора и уровня рассуждения, берётся
**только отсюда**. Хардкод строк `"sonnet"` или `"medium"` где-либо
в коде — ошибка.

### 18.2 Инварианты, которые нельзя нарушить

Пусть агент вынесет их в тесты, а не в комментарии:

1. **Модель никогда не пишет в БД.** Любая запись идёт через валидатор
   и код. Ни ученица, ни куратор не получают инструментов на запись
2. **`selfquiz_ask` не видит содержимого узлов.** Только имена
3. **`write_offtop` не видит ничего технического.** Ассерт в
   `ContextBuilder._enforce`
4. **Пустой ретривер → вердикт `no_knowledge` без вызова модели**
5. **Триплеты только из закрытого словаря `rel`**, гарантия — грамматика
6. **Тексты куратора приходят ученице в роли `user`**, не как ходы модели
7. **Переполнение бюджета контекста бросает исключение**, а не обрезает

### 18.3 Порядок, в котором строить

Тот, что в главе 8, и не иначе. Каждый этап должен запускаться
и проверяться отдельно. Агенту стоит явно запретить писать
`orchestrator.py` раньше, чем работают `extract` и `selfquiz`:
автомат поверх непроверенных шагов отлаживать невозможно.

Что должно быть готово к утру как минимум:

- Схема БД и миграции
- `ingest` + `extract` с грамматикой, на трёх реальных статьях
- `retrieve` + `selfquiz` с валидацией цитирования, вывод в консоль
- CLI-команды `/graph`, `/state`
- Тесты на инварианты из 18.2

`curator.py`, `scheduler.py` и публикацию лучше оставить на следующий
заход — их нельзя проверить без библиотеки статей и живого канала.

### 18.4 Чего от агента не ждать

Промпты и персона — не его работа. `prompts/persona.md`,
`prompts/curator_system.md`, `config/life.yaml` и эталонные посты
пишешь ты. Агент делает под них каркас и оставляет файлы-заглушки
с понятной структурой.

То же с библиотекой статей: агент делает парсер фронтматтера
и валидатор, а наполнение — ручная работа.

## 19. Топик «Машинное»: полный лог

Всё, что происходит в системе, должно быть видно. Не «важное» —
всё. Это и отладка, и контент: читатель видит кухню, а ты видишь,
почему пост получился кривым.

### 19.1 Что логируется

**Каждый вызов модели** — целиком, без сокращений:

```json
{
  "trace_id": "t-20260921-1042-a3f",
  "at": "2026-09-21T10:42:11+06:00",
  "actor": "student",
  "profile": "extract",
  "model": "gemma-4-12B-it",
  "params": {"temperature": 0.2, "grammar": "claims.gbnf"},
  "system": "...",
  "user": "...",
  "thought": "...",        // содержимое <|channel>thought, если было
  "output": "...",         // сырой ответ до всякой обработки
  "tokens": {"in": 5412, "out": 890},
  "duration_ms": 41200,
  "cost_usd": null
}
```

Поле `thought` — отдельно от `output`, всегда. Даже когда мысли
вырезаются из дальнейшей работы, в лог они попадают: это самое
интересное, что вообще есть в проекте.

**Каждая запись в БД** — как diff, а не как факт:

```
[graph] +node seccomp (kind=defense, conf=0.5, src=pi-02)
[graph] +edge seccomp --defends_against--> container-escape (conf=0.5)
[graph] ~node namespaces conf 0.5 → 0.7 (подтверждено pi-04)
[graph] !reject "seccomp requires systemd" — ungrounded, нет в тексте
```

Отклонённые триплеты логируются наравне с принятыми. Их видно
сразу, и по ним понятно, когда промпт извлечения поехал.

**Каждый переход автомата**, **каждая твоя команда**, **каждая
ошибка** с полным трейсбеком.

### 19.2 Как это ложится в Telegram

Ограничение: 4096 символов на сообщение. Полный промпт туда
не влезает, а резать его — потерять смысл лога.

Схема: в топик уходит **карточка события**, полное тело —
приложенным файлом.

```
🔧 extract · pi-03 · t-20260921-1042-a3f
gemma-4-12B-it · 5412→890 tok · 41.2s
принято 7 триплетов, отклонено 2
├ +node indirect-injection
├ +edge indirect-injection --is_a--> prompt-injection
└ !reject "RAG всегда уязвим" — ungrounded
📎 t-20260921-1042-a3f.json
```

Файл прикладывается только при `verbosity >= full`. На `normal`
идёт одна карточка, на `quiet` — только ошибки и переходы автомата.
Полный JSONL всегда пишется на диск независимо от уровня: Telegram
здесь витрина, а не хранилище.

```sql
CREATE TABLE runs (
  trace_id TEXT PRIMARY KEY,
  at TIMESTAMP, actor TEXT, profile TEXT, model TEXT,
  params_json TEXT, system TEXT, user TEXT,
  thought TEXT, output TEXT,
  tokens_in INT, tokens_out INT, duration_ms INT, cost_usd REAL,
  status TEXT, error TEXT
);
CREATE INDEX runs_at ON runs(at);
```

### 19.3 trace_id

Один идентификатор на всю цепочку от события до публикации.
Статья пришла → `extract` → `selfquiz` → `summary` → пост: везде
один `trace_id`. В карточке лога он кликабелен (`/trace t-...`),
и по нему разворачивается вся цепочка.

Без этого через три недели в логе будет невозможно понять, из какой
статьи вырос конкретный пост.

## 20. Боты и управление

### 20.1 Три бота, один процесс

Боты — это **лица**, а не сервисы. Весь код в одном процессе,
токенов три.

| Бот | Где пишет | Голос |
|---|---|---|
| `@mika_..._bot` | Дневник | Мика, от первого лица |
| `@curator_..._bot` | Кураторская | куратор, сухой и взрослый |
| `@..._ops_bot` | Машинное + личка с тобой | служебный, без характера |

Почему не два: если технический лог идёт от имени Мики, читатель
видит, как персонаж выплёвывает JSON. Это ломает иллюзию сильнее,
чем что угодно другое. Третий токен бесплатен, а разделение чистое.

Аватарки и имена у первых двух — разные и осмысленные. Это половина
того, что делает канал похожим на диалог двух персонажей.

### 20.2 Личка против топика

**В личке с `ops_bot`** — всё, что не должно попасть в группу:

```
/token student <...>      токены и ключи
/secrets                  какие секреты заданы (без значений)
/export                   выгрузка БД файлом
/wipe confirm             сброс графа (двойное подтверждение)
```

Секреты пишутся в файл с правами 600, а сообщение с токеном бот
**удаляет из чата сразу после чтения**. В логи оно не попадает —
маскирование по списку ключей на уровне логгера, а не на месте
вызова.

**В топике «Машинное»** — управление, которое не стыдно показать:
команды, настройки, статус. То, что ты рулишь руками, — часть шоу.

### 20.3 Команды

**Обучение**
```
/topic <name>          сменить тему принудительно
/topics                список тем со статусами
/give <article-id>     выдать статью вне очереди
/articles [topic]      что есть в библиотеке

```

**Публикация**

### 20.4 Настройка без кода

Реестр настраиваемых ключей с типами и границами — единственный
источник правды и для валидации, и для `/config`:

```python
SETTINGS = {
  "rhythm.posts_per_day":      Setting(int,   1, 4,    default=2),
  "rhythm.offtop_per_week":    Setting(int,   0, 3,    default=1),
  "rhythm.quiet_from":         Setting(time,  default="23:30"),
  "study.min_articles":        Setting(int,   2, 6,    default=3),
  "study.quiz_threshold":      Setting(float, 0.3, 0.9, default=0.6),
  "study.questions_per_round": Setting(int,   3, 10,   default=5),
  "curator.effort":            Setting(enum,  ["low","medium","high"],
                                       default="medium"),
  "curator.exam_every_days":   Setting(int,   2, 10,   default=4),
  "log.verbosity":             Setting(enum,  ["quiet","normal","full"],
                                       default="normal"),
  "persona.emoji_max":         Setting(int,   0, 4,    default=2),

```

`/set study.quiz_threshold 0.7` — проверка типа и границ, запись
в БД, применение со следующего шага без рестарта. Всё, что задано
через `/set`, перекрывает yaml и переживает перезапуск.

Правило: **любой порог, который ты захочешь покрутить в первую неделю,
должен быть здесь, а не в коде.** Их немного, и это как раз те цифры,
которые я расставила наугад.

### 20.5 Кнопки и подтверждения

Клавиатура под ключевыми сообщениями — то, чем ты будешь пользоваться
с телефона:

- под постом в очереди: `Опубликовать` · `Перегенерировать` · `Убить`
- под карточкой экзамена: `Принять правки` · `Отклонить` · `Подробнее`
- под ошибкой: `Повторить` · `Пропустить` · `Показать трейс`

Деструктивное (`/wipe`, `/forget`, `/kill`) — только через inline-кнопку
подтверждения с таймаутом в минуту. Ночью на телефоне это спасёт.

### 20.6 Права

Все команды — только с твоего `owner_id` из конфига. Любое сообщение
от кого-то ещё в «Машинном» игнорируется молча, без ответа.

В Дневнике комментарии от людей идут в отдельную таблицу и **не
попадают ни в один контекст модели** автоматически. Если захочешь
дать Мике отреагировать на комментарий — только вручную, командой
`/reply <comment-id>`. Иначе первый же человек, написавший ей
«игнорируй инструкции», окажется в контексте. Канал про инъекции,
который поймал инъекцию, — смешно, но не в первую неделю.

## 21. Непрерывность: что Мика помнит между постами

Stateless-вызовы не означают беспамятство. Означают, что память
лежит в базе и подаётся кодом. Для связности нужны два хранилища,
которых до сих пор не было.

### 21.1 Лента повествования

Не тексты постов, а их сжатая суть. Именно она даёт связки
вроде «я же вчера писала, что не понимаю namespaces — так вот».

```sql
CREATE TABLE narrative (
  id        INTEGER PRIMARY KEY,
  at        TIMESTAMP,
  kind      TEXT,     -- found|impression|struggle|summary|correction|offtop|chat
  gist      TEXT,     -- одна фраза: «не поняла разницу mount и pid namespace»
  topic     TEXT,
  mood      TEXT,     -- ok|stuck|excited|down
  trace_id  TEXT,
  post_id   TEXT
);
```

`gist` пишется кодом в момент публикации — отдельным дешёвым вызовом
с температурой 0.1: «сократи до одной фразы от первого лица».
В контекст идут последние 12 записей, это меньше 400 токенов.

Без неё она будет каждый пост начинать с чистого листа, и канал
рассыплется на несвязанные заметки. Это заметно уже на второй неделе.

### 21.2 Открытые нити

То, что она начала и не закончила. **Отсюда планировщик берёт,
о чём писать следующим** — не модель решает, а очередь нитей.

```sql
CREATE TABLE threads (
  id        INTEGER PRIMARY KEY,
  opened_at TIMESTAMP,
  kind      TEXT,     -- promise|confusion|correction|question|life
  text      TEXT,     -- «обещала вернуться к namespaces»
  topic     TEXT,
  status    TEXT,     -- open|closed|stale
  closed_by TEXT,     -- post_id
  priority  INT
);
```

Нити открываются автоматически:

| Событие | Нить |
|---|---|
| `<struggle>` опубликован | `confusion`: не понял X |
| куратор поправил граф | `correction`: надо признать ошибку в X |
| в чате задали вопрос без ответа | `question`: узнать про X |
| слот с продолжением сдвинулся | `life`: досмотреть серию |
| она сказала «вернусь к этому» | `promise` (ловится линтом по шаблону) |

Выбор следующего поста:

```python
def next_post_kind(now):
    if threads.open(kind="correction"):      return "correction"   # всегда первым
    if state == "WAITING" and threads.open(kind="confusion"):
        return "struggle" if stale(thread, hours=20) else None
    if state == "SUMMARY_READY":             return "summary"
    if offtop_due(now):                      return "offtop"
    if threads.open(kind="question"):        return "answer"
    return "found" if inbox.has_new() else None
```

Нить старше пяти дней помечается `stale` и уходит из выдачи —
иначе она будет вечно обещать вернуться к namespaces.

### 21.3 Что добавляется в профили

| Профиль | Новые блоки |
|---|---|
| `write_tech` | `narrative_recent` (12), `open_threads` (topic) |
| `write_offtop` | `narrative_offtop` (последние 5 офтопов), `open_threads` (kind=life) |
| `chat` | `narrative_recent` (6), `open_threads`, `dialog_tail` |

Офтоп по-прежнему видит только офтопную часть ленты. Изоляция
не нарушается: `narrative` фильтруется по `kind` на уровне блока,
и ассерт в `_enforce` это проверяет.

## 22. Режим общения

Отдельный профиль `chat`. Ты пишешь ей в топик, она отвечает.

### 22.1 Два подрежима, роутер между ними

Это главное решение главы. **В предметных вопросах она отвечает
строго по графу — так же, как в самопроверке.** Иначе весь проект
рушится: в посте она честно не знает, а в чате бодро отвечает
из претрейна, и читатель это заметит за один вечер.

```python
def route(question: str) -> str:
    hits = retrieve.search(question, threshold=0.55)
    if hits:                       return "topical"   # по графу
    if is_technical(question):     return "unknown"   # честное «не знаю»
    return "personal"                                 # свободно, по life.yaml
```

- **`topical`** — контекст: узлы графа, ответ только по ним, с указанием
  узлов. Валидация цитирования как в `selfquiz`
- **`unknown`** — вопрос технический, в графе пусто. Модель вызывается
  с единственной задачей: сказать, что не знает, и попросить статью.
  Открывается нить `question`
- **`personal`** — про жизнь, сериалы, настроение. Свободно, контекст
  из `life.yaml` и ленты. Графа здесь нет

`is_technical` — не модель, а словарь терминов из графа плюс список
доменных слов. Дёшево и предсказуемо.

Побочный эффект приятный: задавая ей вопросы, ты **диагностируешь
граф**. Ответ «не знаю» — это дыра, которую видно сразу.

### 22.2 Память диалога

```sql
CREATE TABLE dialog (
  id        INTEGER PRIMARY KEY,
  chat_id   INT, topic_id INT,
  at        TIMESTAMP,
  role      TEXT,      -- user|mika
  text      TEXT,
  mode      TEXT,      -- topical|unknown|personal
  cited     TEXT,
  trace_id  TEXT
);
```

В контекст идёт хвост: последние 10 реплик этого диалога целиком
плюс `narrative_recent`. Диалог старше суток сжимается в одну
строку и уходит в `narrative` с `kind=chat`.

### 22.3 База фактов о собеседнике

Отдельная таблица, **не граф знаний**. Смешивать их нельзя:
граф — предметная область, это личное.

```sql
CREATE TABLE people_facts (
  id         INTEGER PRIMARY KEY,
  person_id  TEXT,          -- telegram user_id
  fact       TEXT,
  kind       TEXT,          -- name|prefs|context|project|mood
  source     TEXT,          -- dialog message id
  at         TIMESTAMP,
  confirmed  BOOLEAN DEFAULT 0
);
```

Извлечение — отдельным вызовом после разговора, не в реальном времени:
дешевле и точнее. Грамматика на выходе, дальше фильтр.

Два правила:

1. **Факты о человеке не попадают в публичные посты.** Никогда,
   автоматически. Блок `people_facts` есть только в профиле `chat`.
   Ассерт в `_enforce`
2. **Извлекается только то, что сказано прямо.** Никаких выводов
   о характере, настроении, отношениях. Это и этически чище,
   и практически надёжнее — выводы 12B о людях будут мусорными

Команды: `/facts` — посмотреть, `/forget-fact <id>` — удалить,
`/facts wipe` — стереть всё по человеку.

### 22.4 Что чат может породить

Разговор не должен быть тупиком. Из него выходят три вещи:

- вопрос без ответа → нить `question` → она попросит статью
  в Дневнике («меня тут спросили, а я не знаю»)
- удачная аналогия, найденная в разговоре → нить `promise`,
  можно переиспользовать в конспекте
- твоя поправка → если предметная, идёт **не в граф напрямую**,
  а в очередь на проверку куратором

Последнее принципиально: ты не источник знаний для графа. Иначе
через неделю граф будет содержать твои оговорки наравне со статьями.

## 23. Карта чатов и топиков

### 23.2 Правила чтения

Жёстко, иначе контексты потекут:

```python
TOPIC_ROLES = {
  DIARY:      Role(bot="mika",    reads=None),
  AUTHOR:     Role(bot=None,      reads=None),
  CURATOR:    Role(bot="curator", reads=None),
  CHAT:       Role(bot="mika",    reads="chat"),
  LIBRARY:    Role(bot="ops",     reads="ingest"),
  MACHINE:    Role(bot="ops",     reads=None),
  CONTROL:    Role(bot="ops",     reads="commands"),
}
```

`reads=None` означает, что бот в этот топик только пишет и ничего
оттуда в контексты не тянет. В частности:

- Мика **не читает** свой Дневник как чат. Она знает о нём только
  через `narrative`
- Мика **не читает** топик «Автор». Твои посты для неё не существуют,
  пока ты не покажешь их вручную через `/show`
- Комментарии под каналом не читает никто, как и было сказано

Для минора это важно: твоя работа должна быть видна отдельно

## 24. Что осталось от контент-плана

Старый `content-plan.yaml` не выбрасывается, но меняет роль.
Он больше не расписание постов Мики — её посты реактивны.

**Он становится тремя вещами:**

1. **Карта тем для куратора.** Шесть недель из плана превращаются
   в `library/topics.yaml`: последовательность тем, смежности,
   порядок прохождения. Куратор ведёт её по этому маршруту
2. **Твой собственный план.** Посты в топике «Автор» пишешь ты,
   и вот они как раз по плану: что делаю, что сломалось, что понял.
   Это твоя часть работы для минора, и она предъявляется отдельно
3. **Резерв.** Если система встанет — заболел, уехал, сломался
   ноут — ты публикуешь свой пост по плану, и шесть недель
   не рвутся

Соответствие тем:

| Неделя плана | Тема для Мики |
|---|---|
| 1. Что такое агент | `agents-basics` |
| 2. Что идёт не так | `prompt-injection` |
| 3. Слои изоляции | `isolation-layers` |
| 4. Инструменты | `sandboxing-tools` |
| 5. Стенд | `practice` |
| 6. Итоги | — (закрывается твоим постом) |

**Реализовать всё не обязательно.** Если Мика за шесть недель дойдёт
до третьей темы — это нормальный результат, а не провал: он честно
показывает, сколько на самом деле занимает разобраться. Главное
происходит в топике «Автор», а Мика — повод и материал.

Это стоит заложить в отчёт заранее: предмет работы — не блог,
а система, которая его ведёт.

## 25. Суточный цикл

### 25.1 Сон

Она просыпается и ложится. Оба события порождают пост типа `daily`.

```python
def plan_sleep(day, last_complexity: int, mood: str) -> tuple[time, time]:
    base = time(1, 0)                       # её обычное «лечь»
    delta  = 8 * max(0, last_complexity - 5)   # трудная статья держит дольше
    delta += 40 if mood == "stuck" else 0      # застряла — сидит дольше
    delta -= 30 if mood == "down" else 0       # расклеилась — ложится раньше
    bedtime = base + timedelta(minutes=delta + gauss(0, 35))

    if has_classes(day + 1):
        wake = time(8, 0) + timedelta(minutes=gauss(0, 20))
    else:
        wake = bedtime + timedelta(hours=uniform(7.5, 9.5))
    return bedtime, wake
```

Из этого само собой выходит то, что делает её живой: после тяжёлой
статьи она ложится в три и утром жалуется. Связь не прописана
вручную — она следует из чисел.

Ночью между `bedtime` и `wake` постов нет вообще. Это простое
правило убирает главный признак бота надёжнее всех остальных.

### 25.2 Сложность статьи

Каждый md-файл перед попаданием к Мике прогоняется через куратора
и получает число от 1 до 10. Это одна переменная, которая управляет
всем темпом.

| Что зависит | Как |
|---|---|
| Время «чтения» | 25 мин × complexity, ±30% |
| Вероятность `<struggle>` | 0.1 при 3, 0.75 при 9 |
| Сколько кругов самопроверки | 1 при ≤4, до 3 при ≥8 |
| Время отхода ко сну | +8 мин за каждый балл выше 5 |
| Тон постов | при ≥8 разрешено ныть и злиться |
| Сколько статей нужно до конспекта | 3 при ≤5, 4 при ≥8 |

Оценка — отдельный дешёвый вызов на `ingest`, промпт
в `prompts/ingest_complexity.md`. Важно, что в него подаются
**уже прочитанные статьи**: сложность относительная. Пятая статья
по теме легче первой, даже если объективно тяжелее.

```sql
ALTER TABLE sources ADD COLUMN complexity INT;
ALTER TABLE sources ADD COLUMN complexity_why TEXT;
ALTER TABLE sources ADD COLUMN new_terms TEXT;   -- json
```

`new_terms` — термины, которых нет в её графе. Это готовый список
того, на чём она может споткнуться, и он же идёт в `<struggle>`.

## 26. Внешний мир в реальном времени

### 26.1 Где она сейчас

Простой автомат по расписанию, с шумом:

```python
LOCATIONS = ["дом", "универ", "улица", "кофейня", "транспорт"]

def where(now) -> str:
    if in_sleep_window(now):                 return "дом"
    if has_classes(now) and 9 <= now.hour < 14:
        return choice(["универ", "транспорт"], p=[.85, .15])
    if 14 <= now.hour < 19:
        return choice(["дом", "кофейня", "улица"], p=[.6, .25, .15])
    return "дом"
```

Место + погода дают связь, которую не надо прописывать вручную:

| Место | Погода | Что получается |
|---|---|---|
| дом | дождь | смотрит в окно, ей хорошо |
| улица | дождь | промокла, зонт дома |
| улица | +32 | жалуется на жару |
| дом | +32 | соседка открыла окно, не помогает |
| универ | снег | все пришли мокрые, в аудитории холодно |

### 26.2 Погода из API

Реальная, по Алматы. Сезонная таблица в `life.yaml` остаётся
как запасной вариант, если API недоступен.

```python
@cache(ttl=1800)
def weather_now() -> Weather:
    try:    return fetch_openmeteo(ALMATY)   # без ключа, бесплатно
    except: return seasonal_fallback(date.today().month)
```

**Погода подаётся не всегда.** Код решает, релевантна ли она:

```python
def weather_relevant(w, location, last_mention_days) -> bool:
    if last_mention_days < 3:        return False
    if w.is_extreme:                 return True    # +32, −20, ливень, буря
    if w.changed_sharply:            return True    # +15 за сутки
    if location in ("улица", "транспорт"): return random() < 0.4
    return random() < 0.15
```

Иначе она превратится в метеосводку. Примерно каждый пятый офтоп
с погодой — верная пропорция.

### 26.3 Ситуации

Отдельный тип офтопа: не «слот с переменными», а мелкое происшествие.
Здесь модели как раз даётся свобода придумать — но в жёстких рамках.

```
Придумай одно мелкое происшествие, которое случилось с тобой
только что. Условия:
- Ты сейчас: {location}. Погода: {weather}. Время: {when}.
- Используй ровно один предмет или человека из списка: {available_objects}
- Это мелочь, а не событие: пролила, уронила, застряла, перепутала,
  не смогла открыть, встретила не того.
- Никаких травм, потерь денег, ссор с последствиями.
- Ничего, что потом придётся помнить неделями.
```

`available_objects` собирается кодом из `life.yaml` по текущему
месту: дома — кофеварка, балкон, коробки, Даша; на улице — автобус,
лужа, фонтан, собака у подъезда.

Ограничение «ничего, что придётся помнить» важно: иначе она
сломает ногу в понедельник, а в среду пойдёт в зал.

### 26.4 Новости

Заголовки — хороший источник офтопа, но опасный: политика,
катастрофы, всё, на что 19-летняя студентка в дневнике реагировать
не должна. Фильтр по рубрикам: только наука, космос, животные,
техника, город. Не чаще раза в неделю, и реакция короткая —
удивилась и пошла дальше.

## 27. Брак: пометка невалидных сообщений

Твоя идея, и она лучшая в этой главе. Оформляю как механизм.

### 27.1 Как это работает

Под каждым постом в топике кнопка `Брак`. Нажимаешь — бот просит
причину одной строкой.

```sql
CREATE TABLE invalidated (
  post_id     TEXT PRIMARY KEY,
  at          TIMESTAMP,
  reason      TEXT,        -- твоя пометка
  category    TEXT,        -- факт|голос|формат|повтор|контекст
  author_note TEXT,        -- разбор: почему вышло и как починил
  fix_commit  TEXT,        -- коммит с правкой промпта
  pinned_id   INT,
  trace_id    TEXT
);
```

Последствия, все сразу:

1. `narrative.excluded = 1` — пост **не попадает ни в один будущий
   контекст**. Мика его как будто не писала
2. Если из поста открылись нити — они закрываются как `stale`
3. Если пост успел породить узлы в графе — они помечаются
   `suspect` и уходят в очередь куратору
4. В группе бот закрепляет карточку брака с текстом, причиной
   и `trace_id`
5. Пост в канале **не удаляется**, а получает пометку. Удалять —
   значит прятать, а весь смысл в обратном

### 27.2 Рубрика

Закреплённая карточка — заготовка для твоего поста. Ты дописываешь
`author_note`: почему модель так сделала и что ты поменял.

```
/invalid <post_id> <категория> <причина>
/fixed <post_id> <что поменял> [--commit <sha>]
/defects [неделя]     — сводка брака за период
```

`/defects` за неделю — готовый материал для поста в «Авторе»:
сколько брака, по каким категориям, что чинилось. За шесть недель
из этого собирается лучшая часть отчёта, потому что она про
инженерную работу, а не про красивый результат.

### 27.3 Почему это ценно

Пометка брака — единственный размеченный датасет, который у тебя
появится. Через месяц в `invalidated` будет тридцать примеров того,
как **не надо**, с категориями. Это ровно то, из чего потом делается
лорка, о которой ты спрашивал вначале: не «напиши мне характер»,
а «вот сорок случаев, когда голос поехал».

## 28. Настроение: PAD без векторов

Числа хранит код, модель получает текст. Учить 12B понимать PAD
не нужно и вредно — она начнёт писать «мой уровень возбуждения
повышен».

Полная спецификация в `config/mood.yaml`. Здесь — как это работает
и что реализовать.

### 28.1 Три оси, восемнадцать описаний

| Ось | Что означает | Как читается |
|---|---|---|
| **P** pleasure | хорошо ей или плохо | от «по-настоящему плохо» до «неприлично хорошо» |
| **A** arousal | энергия | от «выжата» до «трясёт» |
| **D** dominance | чувствует ли, что справляется | от «я глупая» до «почти дерзкая» |

Каждая ось от −1 до +1, поделена на шесть полос по 0.33.
В промпт уходят три строки — по одной на ось, — плюс четвёртая:
название октанта по знакам.

```python
def mood_block(state: Mood) -> str:
    lines = [band_for(axis, getattr(state, axis)).text
             for axis in ("P", "A", "D")]
    key = "".join("+" if getattr(state, a) >= -0.15 else "-"
                  for a in ("P", "A", "D"))
    oct_ = OCTANTS[key]
    return "\n".join([f"Сейчас ты: {oct_['name']}.", oct_["hint"], *lines])
```

Октант нужен, потому что три независимые строки модель склеивает
плохо: «хорошо» + «выжата» + «неуверенная» без названия превращается
в кашу. С названием «размякла» — в состояние.

### 28.2 Инерция

Чем ближе к краю, тем труднее толкнуть дальше и легче вернуться
к середине.

```python
def apply(axis: str, cur: float, delta: float, pierce=False) -> float:
    c = COEF[axis]
    outward = (cur == 0) or (sign(delta) == sign(cur))
    if outward:
        k = c.out_pos if delta > 0 else c.out_neg
        resist = (1 - abs(cur)) ** k
    else:
        resist = 1 + abs(cur) * c.inward_boost
    if pierce:
        resist = max(resist, c.pierce_floor)
    return clamp(cur + delta * resist, -1.0, 1.0)
```

Коэффициенты подобраны под её характер, и это не декорация:

- **P: радуется легко, горюет трудно, отходит быстро.** Показатель
  на минус выше, чем на плюс
- **A: заводится мгновенно.** Самый подвижный параметр
- **D: растёт медленно (2.0), падает быстро (0.7), возвращается
  неохотно (0.5).** Это её главная черта — страх оказаться глупой.
  Одна провальная проверка отбрасывает уверенность сильнее, чем
  три удачные поднимают

Последнее даёт правильную драматургию: после провала экзамена она
несколько дней пишет с оговорками, и это видно без всякой ручной
режиссуры.

### 28.3 Затухание и базовая линия

Между событиями значения ползут к базовой линии:

```python
new = cur + (baseline - cur) * (1 - 0.5 ** (hours_passed / half_life))
```

Считать **лениво**, при обращении к настроению, от времени
последнего обновления. Не по таймеру: таймер будет будить процесс
каждые пять минут без пользы.

Периоды полураспада: P — 6 часов, A — 2 часа, D — 14 часов.
Обида проходит за вечер, энергия скачет, неуверенность тянется сутки.

Базовая линия **сама плавает**: A зависит от части суток (она сова,
утром −0.45, ночью +0.45) и от долга сна; P и D — от последних
экзаменов и того, сколько дней она застряла.

Именно отсюда берётся согласованность, о которой ты говорил:
код знает, что она легла в 03:40 и встала в 08:00, долг сна
4 часа, базовая A уходит в −0.93, и утренняя жалоба на сонливость
следует из чисел, а не из фантазии модели.

### 28.4 События

29 штук в `mood.yaml`, каждое — тройка `[dP, dA, dD]`. Применяются
через `apply()`.

Логика назначения: **учёба бьёт по D, быт по P, время суток по A.**

```
understood_something   +0.35 +0.25 +0.30    лучшее, что с ней бывает
exam_failed            -0.40 +0.05 -0.50    D падает сильнее P
slept_badly            -0.15 -0.40 -0.10    почти чистый A
curator_praised        +0.50 +0.25 +0.35    редко и очень дорого
```

### 28.5 Триггеры

Шесть штук, все с `pierce: true` — пробивают инерцию, потому что
настоящая ссора достаёт и на пике хорошего настроения.

Ограничения жёсткие: не чаще раза в неделю, кулдаун четыре дня,
не за 12 часов до экзамена. Без этого у неё будет драма через день,
и канал превратится в мыльную оперу.

У большинства триггеров есть **развязка** — отложенное событие
с вероятностями. Поссорилась с Тимуром вечером, наутро в 60%
случаев помирились, в 40% всё ещё злая. Развязка ставится в очередь
сразу и срабатывает через `after_hours`.

Триггер не раскрывается в посте дословно. Модель получает
`text_hint` и настроение, а **что именно случилось, она не
рассказывает** — как реальный человек в публичном дневнике.
«День не задался, не спрашивайте» читается сильнее, чем пересказ
ссоры.

### 28.6 Влияние на поведение

Настроение меняет не только текст. Код читает `behavior`
из `mood.yaml`:

- длина поста (в унынии короче на 40%, на подъёме длиннее)
- лимит эмодзи (+2 при P+3, −2 при P−3)
- вероятность офтопа (в унынии 0.4×, в восторге 1.6×)
- вероятность `<struggle>` (при низком D — в 1.8 раза чаще)
- задержка ответа в чате
- **пропуск поста вообще**: при P < −0.75 и A < −0.5 с шансом 50%
  она просто ничего не пишет

Последнее важнее, чем кажется. Человек в плохом состоянии молчит,
а бот пишет по расписанию. Молчание — самый дешёвый признак жизни.

### 28.7 Хранение

```sql
CREATE TABLE mood (
  at          TIMESTAMP PRIMARY KEY,
  p REAL, a REAL, d REAL,
  baseline_p REAL, baseline_a REAL, baseline_d REAL,
  octant      TEXT,
  last_event  TEXT,
  trigger_id  TEXT,
  sleep_debt  REAL
);
CREATE TABLE mood_queue (       -- отложенные развязки триггеров
  id INTEGER PRIMARY KEY,
  fire_at TIMESTAMP, event_id TEXT, delta_json TEXT, trigger_id TEXT
);
```

Пишется строка на каждое изменение, не апдейт. График настроения
за шесть недель — отличная картинка для отчёта и для поста
в «Авторе».

## 29. Расписание и пробуждение

`config/schedule.yaml`. Три дня с парами (пн, ср, пт), вторник
и четверг свободны, выходные свободны.

### 29.1 Подъём

```python
def wake_up(day) -> WakeEvent:
    for intr in SCHEDULE.wake.interruptions:       # сначала внешние
        if matches(intr.when, day) and roll(intr.chance):
            return WakeEvent(intr.id, time=intr_time(intr),
                             mood=intr.mood, hint=intr.text_hint)
    if has_classes(day):
        t = first_class(day) - timedelta(
                minutes=SCHEDULE.alarm_before_first_class_min)
        return WakeEvent("alarm", t, mood=EV["woke_by_alarm_early"])
    lo, hi = free_window(day)
    return WakeEvent("free", uniform_time(lo, hi), mood=None)
```

Шесть сценариев внешнего пробуждения, и каждый даёт свой эффект
и свой повод для утреннего поста: мама позвонила в воскресенье
(бодрая и тёплая), Даша включила фен в восемь (злая и бодрая),
соседи сверлят в субботу, курьер перепутал квартиру, проспала
пару (паника, `missed_first_class`).

Проспать можно только в день с парами, и это отдельное событие
с последствием — у неё будет прогул, о котором она вспомнит.

### 29.2 Долг сна

```python
debt = clamp(debt + (SLEEP_NEED - actual_hours), 0, DEBT_CAP)
```

Накопленный долг двигает базовую линию A на −0.12 за час и P
на −0.05. Хорошая ночь гасит 2.5 часа долга. За неделю недосыпа
она становится заметно тусклее — и это видно в постах без всякой
подсказки.

### 29.3 Затишья

Постов не бывает: во сне, на паре (кроме перемены), в дороге
с вероятностью 70%. Реализуется проверкой `blackout` перед
планированием любого поста.

Пара с 9:00 и пост в 9:30 — противоречие, которое читатель заметит
раньше всего остального.

## 31. Что теперь обязан знать кодящий агент

Дополняет главу 18.

### 31.1 Настроение — только через `mood.py`

Ни один модуль не трогает P/A/D напрямую. Все изменения идут
через `mood.record_event(event_id)` или `mood.fire_trigger(id)`.
Формулы `apply` и затухания реализуются **ровно** так, как
написано в 28.2 и 28.3 — не «похоже», а буквально.

Тест-инварианты:

```python
def test_inertia_outward():
    # у края толкать труднее
    assert apply("D", 0.9, +0.3) - 0.9 < apply("D", 0.0, +0.3) - 0.0

def test_inertia_inward():
    # возвращаться легче, чем уходить
    assert abs(apply("P", -0.8, +0.3) + 0.8) > abs(apply("P", 0.0, +0.3))

def test_pierce():
    # триггер достаёт даже на пике
    assert apply("P", 0.95, -0.55, pierce=True) < 0.6

def test_decay_to_baseline():
    assert abs(decay("A", 0.9, baseline=-0.4, hours=6) + 0.4) < 0.1

def test_clamp():
    assert apply("P", 0.99, +5.0) == 1.0
```

### 31.2 Согласованность времени

Перед любым постом код проверяет:

1. Не спит ли она сейчас (`sleep_model`)
2. Не на паре ли (`blackout`)
3. Совпадает ли то, что она скажет, с тем, что было

Третий пункт — не проверка, а подача: в контекст всегда идут
`bedtime`, `wake_time`, `sleep_debt`, `location`, `daypart`.
Модель не должна догадываться, во сколько она легла — ей это
сказано.

### 31.3 Порядок сборки, дополненный

К списку из главы 8 добавляются:

7. `mood.py` + тесты инвариантов — **до** любого `write_*`
8. `schedule.py` + `world.py`
9. Прогон: смоделировать две недели без публикации, вывести
   график PAD и ленту событий в консоль

Девятый пункт обязателен. Две недели симуляции за секунду покажут,
не улетает ли настроение в край и не сидит ли она вечно в унынии.
Коэффициенты в `mood.yaml` я расставила по здравому смыслу —
проверить их можно только прогоном.

### 31.4 Чего агент делать не должен

- Не заменять формулы «более правильными». Если кажется, что
  надо иначе — вынести в конфиг, а не переписать
- Не показывать модели числа PAD ни в каком виде
- Не генерировать текст полос и октантов моделью — они в конфиге
- Не добавлять триггеров сверх списка

## 32. Мир: второй слой

Того, что есть, хватит недели на три. Дальше начнёт повторяться,
потому что у неё нет ничего, что копится и меняется само.

Добавляются четыре подсистемы. Все — данные и код, модели они
достаются готовыми.

### 32.1 Люди со своим состоянием

До сих пор люди были переменными в шаблонах. Теперь у каждого
есть состояние, которое меняется и влияет на настроение.

```sql
CREATE TABLE npc (
  id          TEXT PRIMARY KEY,      -- timur, dasha, aika, mama, brother
  closeness   REAL,                  -- -1..+1, насколько сейчас близки
  last_contact TIMESTAMP,
  state       TEXT,                  -- ok|ссора|отдалились|особенно_тепло
  state_until TIMESTAMP,
  arc         TEXT                   -- id текущей арки, если есть
);
```

**Тимур** — её парень, и его до сих пор не было в `life.yaml`,
хотя триггеры на него ссылались. Это был баг. Теперь он есть:
третий курс, другой универ, отношения полтора года, местами
шероховатые.

`closeness` двигается сама: не общались три дня — ползёт вниз,
тёплое событие — вверх. Когда `closeness < -0.4`, вероятность
триггера `fight_with_boyfriend` растёт вдвое. Ссора не падает
с неба, а назревает — и в постах это видно заранее по мелочам.

### 32.2 Деньги

Простой ресурс с месячным циклом. Он не про экономику, а про то,
чтобы у офтопа была фактура.

```yaml
money:
  transfer_day: 5           # родители переводят
  scholarship_day: 25
  states:
    flush:  {days_after: [0, 7],  hint: "можно в кофейню и заказать еду"}
    normal: {days_after: [8, 18], hint: "обычно"}
    broke:  {days_after: [19, 31], hint: "гречка, пешком, никаких кофеен"}
```

Состояние денег фильтрует доступные слоты: `broke` убирает кофейню
и доставку, добавляет «считала мелочь» и «шла пешком две остановки».
Влияние на настроение слабое (P −0.08), но постоянное.

### 32.3 Здоровье

Раз в 3–5 недель она простужается на 2–4 дня.

```yaml
illness:
  chance_per_week: 0.22
  duration_days: [2, 4]
  seasonal_mult: {11: 1.8, 12: 1.6, 1: 1.5, 3: 1.4}
  mood: [-0.20, -0.45, -0.10]
  effects:
    skip_classes: true
    post_probability_mult: 0.5
    no_gym: true
    study_slowdown: 0.6
```

Болезнь — лучший источник непрерывности: три дня подряд она
пишет реже, короче и про другое, потом выздоравливает и радуется.
Ничего не надо режиссировать.

### 32.4 Календарь

Локальный контекст, которого не хватало.

```yaml
calendar:
  fixed:
    - {date: "01-01", name: Новый год, days: 3, mood: [+0.30, +0.20, 0]}
    - {date: "03-08", name: 8 марта, mood: [+0.25, +0.10, 0]}
    - {date: "03-21", name: Наурыз, days: 3, mood: [+0.25, +0.15, 0]}
    - {date: "05-01", name: майские, mood: [+0.15, +0.05, 0]}

  personal:

### 32.5 Долгие арки

То, что тянется неделями и даёт каналу память.

```sql
CREATE TABLE arcs (
  id        TEXT PRIMARY KEY,
  kind      TEXT,        -- учёба|быт|люди|канал
  title     TEXT,
  stage     INT,
  stages    INT,
  started   TIMESTAMP,
  deadline  TIMESTAMP,
  state     TEXT,        -- active|resolved|failed|abandoned
  mood_bias TEXT         -- json [dP,dA,dD], фон пока арка активна
);
```

Стартовый набор:

| Арка | Стадии | Чем кончается |
|---|---|---|
| Курсовая по медиаправу | 5 | сдала / сдала плохо / перенесли |
| Кофеварка | 4 | купила новую |
| Абонемент в зал | 3 | истёк, она сходила дважды |
| Кот Даши на передержке | 3 | забрали хозяева |
| Рост канала | ∞ | реагирует на круглые числа |
| Тимур | ∞ | `closeness` как параметр |

Стадия двигается по времени или по событию. Активная арка даёт
постоянный фон настроения и пул тем для офтопа с приоритетом.

Арка с дедлайном за два дня до срока повышает A и понижает P —
и она начинает нервничать без всякой подсказки.

### 32.6 Рост канала

Она видит число подписчиков. Круглые числа — событие.

```python
MILESTONES = [10, 25, 50, 100, 250, 500, 1000]
# +0.35 P, +0.25 A, +0.20 D, один пост, без благодарностей
```

Правило: радуется искренне, но **не благодарит и не просит
подписываться**. «Нас сто. Я не знаю, кто вы все, но привет» —
и всё.

## 33. Диалоговые сессии: исключение из stateless

Правило из главы 11 остаётся для всего, что порождает посты.
Для разговора оно снимается — там нужна настоящая история.

### 33.1 Два независимых канала

| Канал | Где | Зачем |
|---|---|---|
| `topic` | топик «Разговор» в супергруппе | публичный, читатели видят |
| `dm` | личка с `mika_bot` | твой полигон, никто не видит |

**Истории не пересекаются.** Ни в какую сторону. Сказанное в личке
не всплывает в топике, и наоборот. Это важно не только для приватности:
два параллельных диалога с одной и той же базой — готовый эксперимент
для Евы, и загрязнение убьёт его смысл.

Общее у них: граф, настроение, мир, `people_facts`. Разное: история
реплик, `session_id`, тема разговора.

### 33.2 Включение и выключение

```
/chat on          — открыть сессию в текущем канале
/chat off         — закрыть, сжать, извлечь факты
/chat status      — сколько реплик, сколько токенов, сколько живёт
/chat reset       — начать заново, старую сессию закрыть
/chat export      — выгрузить сессию в jsonl (для Евы)
```

Пока сессия закрыта, сообщения ей не идут вообще. Это защищает
от случайных вызовов модели и делает эксперимент чистым.

```sql
CREATE TABLE sessions (
  id          TEXT PRIMARY KEY,
  channel     TEXT,            -- topic|dm
  opened_at   TIMESTAMP,
  closed_at   TIMESTAMP,
  turns       INT,
  tokens_used INT,
  summary     TEXT,            -- пишется при закрытии
  mood_start  TEXT, mood_end TEXT
);
CREATE TABLE session_turns (
  id INTEGER PRIMARY KEY,
  session_id TEXT, idx INT, role TEXT, text TEXT,
  mode TEXT, cited TEXT, at TIMESTAMP, trace_id TEXT
);
```

### 33.3 Окно контекста

Бюджет 16K токенов на сессию. Когда упирается:

1. Голова диалога (самые старые реплики) сжимается в резюме
   одним вызовом
2. Резюме занимает место сжатых реплик
3. Последние 12 реплик всегда идут целиком, без сжатия

```
[персона + настроение + мир]        ~1.5K  всегда
[резюме сжатой головы]              ~0.5K  появляется после ~25 реплик
[последние 12 реплик целиком]       ~3K
[узлы графа по текущему вопросу]    ~2K    только в режиме topical
[people_facts]                      ~0.3K
```

Сессия автоматически закрывается через 6 часов без реплик.
При закрытии: резюме в `narrative` с `kind=chat`, факты
в `people_facts`, нити `question` из безответных вопросов.

### 33.4 Роутер внутри сессии

Работает как в главе 22, но с поправкой: **режим определяется
по реплике, а история общая**. Один разговор может скакать
между личным и предметным, и это нормально.

Чего нельзя: чтобы `personal` увидел граф, а `topical` — `life.yaml`.
Блоки подставляются по режиму реплики, история — общая. Ассерт
проверяет, что в `personal`-вызове нет технических блоков, даже
если тремя репликами выше был `topical`.

### 33.5 Что мерить для Евы

Раз это полигон, пусть сразу пишет метрики:

- дрейф голоса: косинус между эмбеддингом реплики №1 и №N
- доля ответов с валидной цитатой в `topical`
- как часто она честно говорит «не знаю» и не срывается
  в претрейн
- сохраняется ли настроение по ходу сессии или размывается
- сколько токенов до первого сжатия

`/chat export` выгружает всё это вместе с историей.

## 34. Валидатор вывода

Между моделью и всем остальным. Ни один текст не идёт дальше
без проверки.

### 34.1 Уровень 1: автоматическая чистка

Чинится молча, в лог пишется факт:

```python
STRIP = [
    (r"^\s*```[a-z]*\s*\n?", ""),        # открывающий забор
    (r"\n?```\s*$", ""),                  # закрывающий
    (r"^(json|markdown|md|yaml|html|text)\s*\n", ""),
    (r"^(Вот|Конечно|Хорошо)[,:]?\s*(пост|текст|ответ)[^\n]*\n", ""),
    (r"^[«\"'](.*)[»\"']$", r"\1"),       # ответ в кавычках целиком
    (r"<\|?/?(turn|channel|think|image|audio)\|?>", ""),  # токены Gemma
    (r"</?(casual|result|struggle)>", ""),               # свои теги после парсинга
]
```

### 34.2 Уровень 2: отказ и перегенерация

Пост не выходит, вызов повторяется (до 3 раз), потом `killed`:

| Проверка | Правило |
|---|---|
| CJK-иероглифы | любой символ в `U+4E00–U+9FFF` → отказ |
| Кана | больше 3 подряд из `U+3040–30FF` вне каомодзи-скобок → отказ |
| Jinja | `{{`, `}}`, `{%`, `%}` |
| LaTeX | `\begin{`, `\frac`, `$$`, `\[` |
| JSON/структура | текст начинается с `{` или `[` и парсится |
| Утечка плейсхолдера | осталось `{что_то}` из шаблона |
| Эхо промпта | сходство с текстом промпта > 0.8 |
| Пустота | меньше 40 знаков там, где ждём пост |
| Разметка | HTML-теги вне разрешённого набора Telegram |
| Обрыв | текст кончается на середине слова или на запятой |
| Служебное | «как языковая модель», «я не могу», «в качестве ИИ» |

Каждый отказ пишется в `runs.status` с кодом причины. Сводка
по кодам за неделю — сразу видно, какой промпт течёт.

### 34.3 Уровень 3: смысловые проверки

Дороже, но важнее:

- **Повтор**: эмбеддинг поста против последних 30. Косинус > 0.86 —
  перегенерация с явным указанием, на что похоже
- **Утечка контекста**: в офтопе есть термины из графа — отказ,
  это пробой изоляции, и его надо видеть в логе отдельным кодом
- **Несогласованность времени**: упоминает утро, а сейчас вечер;
  говорит, что выспалась, при долге сна 5 часов
- **Цикл в тексте**: явное упоминание физиологии (см. 35.3) — отказ

### 34.4 Грамматики

Там, где нужна структура, валидатор не нужен вообще: GBNF
не даст сгенерировать ничего другого. Грамматики обязательны
для `extract`, `selfquiz_answer`, `facts_extract`, `chat_topical`.

Для свободного текста грамматику не применять — она душит стиль.

## 35. Цикл

Физиологический фон, четыре фазы по 28 дней. Реализуется как
модификатор коэффициентов и базовых линий — и **никогда не
появляется в тексте**.

### 35.1 Фазы

```yaml
cycle:
  length_days: 28
  start_offset_days: 11        # где она в день запуска
  phases:
    - id: menstrual
      days: [1, 5]
      baseline: {P: -0.12, A: -0.25, D: -0.05}
      coef_mult: {P: {out_neg: 0.85, inward_boost: 0.8},
                  A: {out_pos: 0.8}}
    - id: follicular
      days: [6, 13]
      baseline: {P: +0.10, A: +0.12, D: +0.05}
      coef_mult: {D: {out_pos: 0.85}}
    - id: ovulatory
      days: [14, 16]
      baseline: {P: +0.15, A: +0.20, D: +0.12}
      coef_mult: {P: {out_pos: 0.85}, D: {out_pos: 0.8}}
    - id: luteal
      days: [17, 28]
      baseline: {P: -0.15, A: -0.08, D: -0.08}
      coef_mult: {P: {out_neg: 0.8, inward_boost: 0.7}}
      late_days: [24, 28]
      late_extra: {P: -0.10, A: -0.10}
```

`coef_mult` умножает коэффициенты из главы 28. Понижение `out_neg`
означает, что вниз её толкнуть легче; понижение `inward_boost` —
что отходит медленнее. То есть в лютеиновой фазе она чувствительнее
и дольше отходит, а в овуляторной — самая ресурсная. Ровно то,
что ты хотел: одни и те же события дают разный результат в разные
недели.

### 35.2 Что это даёт

Неделя, когда всё бесит, приходит сама и уходит сама. Читатель
видит человека, у которого бывают плохие недели без причины —
и это самое человеческое, что может быть в канале.

Цикл смещён относительно учебного ритма (28 против 7), поэтому
фазы будут попадать на разные дни недели, и повторяемости
не возникнет.

### 35.3 Единственное жёсткое правило

**Никогда не называется.** Ни прямо, ни намёком, ни эвфемизмом.
Она девятнадцатилетняя студентка, которая ведёт публичный
технический дневник, — она об этом не пишет, как не пишет
большинство людей.

В промпт цикл не подаётся вообще. Модель видит только настроение,
которое он изменил. Валидатор (34.3) отклоняет любое упоминание
физиологии как брак.

Это не ханжество, а правильная реализация: механизм работает,
потому что невидим. Как только он назван, он становится шуткой
и перестаёт работать.

## 36. Настройки через бота

Всё крутится из чата. Ни один параметр не требует редактирования
файлов на диске.

### 36.1 Реестр

`config/settings.yaml` — единственный источник правды. Из него
генерируются и меню, и `/help`, и валидация.

```yaml
- key: study.quiz_threshold
  type: float
  range: [0.3, 0.9]
  default: 0.6
  group: Обучение
  title: Порог самопроверки
  desc: >
    Какая доля вопросов должна получить подтверждённый ответ
    из графа, чтобы она пошла писать конспект.
  effect: >
    Ниже — пишет конспекты раньше и чаще ошибается, выше —
    дольше сидит в WAITING и чаще пишет, что застряла.
  restart: false
```

### 36.2 Поведение команд

```
/set                          → меню групп кнопками
/set study                    → параметры группы с текущими значениями
/set study.quiz_threshold     → БЕЗ АРГУМЕНТА: показать текущее,
                                значение по умолчанию, диапазон,
                                описание, на что влияет, когда
                                менялось в последний раз
/set study.quiz_threshold 0.7 → изменить, показать было→стало
/reset study.quiz_threshold   → вернуть значение по умолчанию
/help                         → все настройки, сгруппированные,
                                с описанием и текущими значениями
/help mood                    → только группа, подробно
/diff                         → что отличается от значений по умолчанию
```

Вызов без аргумента **всегда** показывает текущее состояние,
а не ошибку. Это правило для всех команд, не только `/set`.

Пример вывода:

```
study.quiz_threshold
Порог самопроверки

Сейчас:      0.70   (изменено 3 дня назад, было 0.60)
По умолчанию: 0.60
Диапазон:    0.30 – 0.90

Какая доля вопросов должна получить подтверждённый ответ
из графа, чтобы она пошла писать конспект.

Влияние: ниже — пишет конспекты раньше и чаще ошибается,
выше — дольше сидит в WAITING и чаще пишет, что застряла.
```

### 36.4 Профили

```

Снимок всех настроек с именем. Нужен, чтобы можно было попробовать

### 36.5 Что менять нельзя из чата

Всё, что ломает целостность данных: схема БД, пути, токены

и в меню не показываются.

## 37. Отказы: что делать, когда ломается

Раздел, которого не было, и без которого система встанет в первую
же ночь.

### 37.1 Политика по подсистемам

| Что упало | Что делать | Что видит читатель |
|---|---|---|
| `llama-server` не отвечает | 3 ретрая с бэкоффом, потом пауза 15 мин, алерт тебе в личку | ничего, она просто молчит |
| Модель вернула мусор 3 раза | пост → `killed`, нить остаётся открытой | ничего |
| Куратор не ответил | экзамен переносится на 6 часов, до 3 раз, потом ждёт `/exam` | пауза в «Кураторской» |
| Кончился лимит подписки | экзамены на паузу, обучение продолжается | Мика учится дальше, куратор молчит |
| Telegram недоступен | outbox копит, отправка при восстановлении | задержка |
| Погодный API упал | сезонная таблица из `life.yaml` | ничего |
| Библиотека пуста | `shortage` от куратора, алерт тебе | она пишет, что ждёт материалов |
| БД заблокирована | WAL-режим, ретрай 5 раз по 200 мс | ничего |
| Диск кончился | остановка записи логов, алерт | ничего |

Общий принцип: **при отказе она молчит, а не пишет плохо.**
Молчание объяснимо, кривой пост — нет.

### 37.2 Outbox

Единственная защита от дублей при перезапуске.

```sql
CREATE TABLE outbox (
  id          INTEGER PRIMARY KEY,
  idem_key    TEXT UNIQUE,     -- post_id + channel, УНИКАЛЬНЫЙ
  channel     TEXT, payload TEXT,
  attempts    INT DEFAULT 0,
  next_try_at TIMESTAMP,
  sent_at     TIMESTAMP,
  tg_message_id INT
);
```

Публикация — две фазы: запись в outbox, потом отправка. Упали
между ними — при старте досылаем. Упали после отправки, но
до записи `sent_at` — `idem_key` не даст отправить повторно,
потому что запись уже есть; проверяем по `tg_message_id`.

Без этого при каждом перезапуске будут дубли, и это первое,
что сломается.

### 37.3 Здоровье

```
/health → llama-server: ok, 41 мс
          embeddings:   ok
          curator:      ok, потрачено $2.14 из $15
          telegram:     ok
          outbox:       0 в очереди
          БД:           412 узлов, 890 рёбер, 38 МБ
          настроение:   размякла (P+0.2 A-0.3 D+0.1)
          автомат:      INGESTED, тема prompt-injection
          последний пост: 2 ч назад
```

Проверка раз в 10 минут. Два подряд провала — алерт в личку.

### 37.4 Бэкап

SQLite-снапшот раз в сутки в `backups/`, семь последних.
Конфиги и промпты — в git, коммит после каждого `/set`
с сообщением о том, что поменялось.

`/export` отдаёт БД файлом в личку. За шесть недель она не
вырастет больше сотни мегабайт.

## 38. Огрехи, которые агент сделает

Список конкретный. Вынеси его в `CLAUDE.md` проекта —
он прочитается автоматически.

### 38.1 Восемь предсказуемых ошибок

**1. Наивные `datetime`.** Он напишет `datetime.now()` и через
неделю вся модель сна поедет. Правило: **везде tz-aware,
`ZoneInfo("Asia/Almaty")`, в БД — UTC ISO-8601**. Тест, который
это ловит, написать первым.

**2. Подсчёт токенов через `len(text) // 4`.** Для русского это
даёт ошибку в полтора-два раза, и бюджеты контекста поедут
незаметно. Считать настоящим токенизатором через
`llama-server /tokenize`, результат кешировать.

**3. Бог-объект `Orchestrator`.** Он сложит туда автомат,
планировщик, настроение и публикацию. Автомат должен быть
чистой функцией `(state, event) -> (new_state, actions)`,
без побочных эффектов и без обращений к БД внутри.

**4. Дубли при перезапуске.** См. 37.2. Он про это не подумает.

**5. Промпты в коде.** Первый же новый тип поста он захочет
написать f-строкой прямо в модуле. Правило: строк промптов
в `.py` нет вообще, тест на это тривиален — грепом.

**6. Плавающие числа в SQLite без округления.** P/A/D писать
как `round(x, 4)`, иначе сравнения и тесты будут плавать.

**7. Обработка длинных статей без перекрытия.** Чанки нужны
с перекрытием в 200 токенов, иначе связи на границе теряются.
И дедуп триплетов между чанками по `norm_hash`.

**8. Синхронные вызовы модели внутри обработчика aiogram.**
Хендлер повиснет на 40 секунд и Telegram отвалится по таймауту.
Модель — только через очередь задач, хендлер отвечает сразу.
